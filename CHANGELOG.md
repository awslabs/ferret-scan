### 🔒 Security

- **web:** bind to loopback (`127.0.0.1`) by default. Closes [TM-01](THREAT_MODEL.md). Container runtimes (Docker/Podman) auto-detected via `/.dockerenv` or `FERRET_CONTAINER_MODE=true` env var keep binding to `0.0.0.0` so port-publishing semantics work; bare-metal users get loopback-only by default. New `--bind <addr>` flag for explicit override (with stderr warning when bound to a non-loopback interface).
- **web:** add Origin/Referer validation on POST/PUT/DELETE/PATCH for `/scan` and `/suppressions/*`. Closes [TM-02](THREAT_MODEL.md). Non-browser callers (curl, scripts) that send neither header are allowed — they aren't subject to CSRF.
- **web:** emit baseline security headers on every response — `Content-Security-Policy` (`default-src 'self'` with `'unsafe-inline'` for the existing template), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`. Closes [TM-03](THREAT_MODEL.md). Strict CSP (no `'unsafe-inline'`) deferred pending template refactor — tracked as TM-05.
- **web:** suppression endpoints now inherit the loopback trust boundary. Closes [TM-04](THREAT_MODEL.md).

### ✨ New Features

- **video:** scan and redact `.3gp`/`.3g2`, and read the Apple `keys`/`ilst` metadata that iPhone and macOS recordings actually use. Four separate gaps in the same container, each measured on a real file. **`.3gp`/`.3g2` were not scanned at all** — the same ISO base media container as `.mp4` with a 3GPP brand — and the failure was SILENT: a real ffmpeg-written `.3gp` carrying an SSN in its 3GPP `dscp` box reported `No matches found.` at exit 0, with `--fail-on-incomplete` also exiting 0 and disclosing nothing, so the value was neither reported nor redacted. Registering the extension proved necessary but not sufficient: the twelve **3GPP asset boxes** (`titl` `dscp` `cprt` `auth` `perf` `gnre` `albm` `yrrc` `kywd` `rtng` `clsf` `perm`, per 3GPP TS 26.244) use a `[version][flags][language][NUL-terminated UTF-8]` payload, not the QuickTime `[length][language][text]` form, so with the extension registered and the boxes unhandled the file reported `Status: Success  MimeType: video/3gpp` and still produced zero findings — a "supported" format extracting nothing, whose clean result then looks authoritative. **Apple's `keys`/`ilst` pair** was unreachable four times over: `parseMoovBoxWithContext` had no `meta` case so a `moov`-level `meta` was never visited; `parseMetaBoxWithContext` skipped four version/flags bytes unconditionally, which is right for an ISO FullBox but wrong for QuickTime's plain container, so it read the first child's type `hdlr` AS ITS SIZE (0x68646c72 = 1,751,411,826) and abandoned the box; `keys` was never decoded into the index→name map that an `ilst` item's numeric type refers to; and an index-typed item fell through to a `default` arm gated on a length-only `isFourCC`, landing under a key made of raw bytes. The reader did not merely lose those values — `searchAppleMetadataInData` scraped raw text for `com.apple.quicktime.<field>` and took the bytes that follow, which in a keys table is *the next key's name*, so on a real macOS recording `CameraMake` read `m.apple.quicktime.model`, `CameraModel` read `m.apple.quicktime.software` and `CreationDate_Apple` read the literal atom type `data`, against true values `Apple`, `Mac16,6` and `macOS 15.2 (24C101)`. The scrape now stands down for any key the table answered. Also: `trak > udta` and `trak > meta` are read (`udta` was movie-level only, so a per-track comment was invisible); the eleven inner box walkers now honour the two special ISO size words via a shared reader, where a size of `1` previously failed the `size < 8` check and **ended the walk**, taking every later sibling with it; a `data` box's well-known type indicator is honoured so a binary payload is no longer stringified into the scanned text, while a mislabelled UTF-8 payload is still read; `parseDate` accepts Apple's colon-less zone offset; and the video redactor claims `.3gp`/`.3g2`, without which a newly-found value was reported and then disclosed as `no redactor registered for file type: .3gp`. Verified end to end: redacting a real `.3gp` writes a same-size file that `ffprobe` still recognises with the cleartext gone. Closes [#431](https://github.com/awslabs/ferret-scan/issues/431) and [#400](https://github.com/awslabs/ferret-scan/issues/400).
- **cloud-resources:** new Cloud Resources Validator detects cloud provider resource identifiers across six major cloud platforms. Supported providers: AWS (ARNs with 12-digit account IDs), Azure (Resource IDs with subscription UUIDs), GCP (resource names with project IDs), OCI (OCIDs), IBM Cloud (CRNs), and Alibaba Cloud (ARNs). Key features: provider-specific metadata extraction (account ID, resource type, region), confidence scoring with contextual analysis, configurable per-provider enable/disable, and custom pattern support via configuration. New validator ID: `CLOUD_RESOURCES`.
- **stdin:** read content to scan from standard input via `--stdin` or the POSIX-style alias `--file -`. Content is treated as plain text and findings are labelled `<stdin>` (configurable via `--stdin-name`). Useful for `git diff | ferret-scan --stdin`, scanning command output, and lambda/IPC callers that already have content in memory. Mutually exclusive with `--file <path>`, positional file args, and `--web`. Max input size: 100 MB.
- **stdin redaction (streaming gateway):** combine `--stdin` with `--enable-redaction` to act as a streaming redactor — redacted content streams to stdout while findings go to stderr (or `--output <file>` if specified). All three plaintext strategies (`simple`, `format_preserving`, `synthetic`) are supported. Suppressed matches pass through unmodified. When findings stream to stderr alongside redacted content on stdout, human-readable progress lines are suppressed so the findings document remains parseable (canonical shape: `... --enable-redaction --format json 2> findings.json > clean.txt`). When stdout is a terminal (interactive use, no redirect), findings are replaced by a one-line hint pointing at the pipe shape — this matches the `git diff` / `jq` convention of adapting output to the consumer.
- **api:** new `core.ScanContent(content, ContentScanConfig)` entry point for in-process callers — scans an in-memory buffer using the same validator pipeline as `ScanFile` but bypasses the path-driven file router.
- **api:** new `plaintext.PlainTextRedactor.RedactString(content, matches, strategy)` exposes pure in-memory redaction without requiring an output manager — the same code path that drives streaming stdin redaction is now available to lambda / gateway callers.
- **api:** new `redact.ValidCheckNames()` returns the sorted validator IDs accepted in `EngineOptions.Checks`. `NewEngine` silently drops names it doesn't recognize and only errors when the resulting set is empty, so a typo in a mixed list (e.g. `{"CREDIT_CARD", "emial"}`) otherwise fails *open* — the misspelled validator is quietly disabled and that data type passes unredacted. Callers wanting fail-closed behaviour can validate their `Checks` against this list and reject unknown names before constructing the engine. The `lambda-redact` example now does exactly this at `init()`.
- **explain:** new `--explain` flag annotates each finding with a plain-language rationale, a verdict (`likely_real` / `likely_test` / `uncertain`), and a drafted suppression reason. Fully offline and deterministic — it only re-phrases signals the detection engine already computes (validation checks, vendor, context impact, file location); no network calls, no new dependencies, nothing leaves the host. Off by default. Renders in text (verbose + pre-commit), JSON/YAML (first-class `explanation` field), SARIF (result message + structured property), and gitlab-sast (description); with `--generate-suppressions`, generated rules carry the drafted per-finding reason. A HIGH-confidence finding is never glossed as `likely_test`, so the verdict can't talk a reviewer out of a real finding. New `internal/explain` package (`Explainer`, `SignalSynthesizer`).
- **api (pkg/scan):** `TextOptions`, `FileOptions` and `RedactFileOptions` gain `ConfigPath string` and `DisableConfigDiscovery bool`, so an embedded consumer can pin the config or opt out of ambient discovery entirely. Previously all three called `config.LoadConfigOrDefault("")` unconditionally with no config field on the options structs, so detection depended on the calling process's **working directory** with no way to pin it, no way to request built-in defaults, and no way to write a hermetic test. Verified with an identical `ScanText` call differing only in CWD: `findings=1` from one directory, `findings=0` from another holding a `.ferret-scan.yaml` with `disabled_types`. Same shape as the `redact.ValidCheckNames()`/`SOCIAL_MEDIA` case — a successful call, an empty finding list, input treated as clean — except the cause was ambient rather than in the caller's arguments, so the caller could neither detect nor prevent it. Both fields default to zero, so **existing callers are unaffected**: an empty `ConfigPath` keeps the historical discovery behaviour. `DisableConfigDiscovery` takes precedence when both are set, being the stricter request.

### 🐛 Bug Fixes

- **redaction:** OpenDocument files are now redacted. No redactor claimed `.odt`/`.ods`/`.odp`, so every ODF finding was reported and then **left in cleartext** — `no redactor registered for file type: .odt`, 7 reported values, no output written. Disclosed rather than silent, which is why it ranked below the silent-miss issues, but a reported value that is never removed is still cleartext; and [#528](https://github.com/awslabs/ferret-scan/issues/528) had just widened it by making the `.ott`/`.ots`/`.otp` templates scannable, so the count of reported-and-abandoned values grew before anything could remove them. Registering the extension would NOT have been enough: the office redactor is written against OOXML part names (`word/document.xml`, `xl/sharedStrings.xml`) and OOXML text elements (`w:t`), none of which exist in ODF, so `.odt` pointed at it unchanged would open the package, match no part, and write output byte-identical to the input **while reporting success** — the shape this repo has fixed twice. ODF is handled as one document type rather than three, because `content.xml` and `meta.xml` are the same parts whatever the document is: a spreadsheet cell is `table:table-cell > text:p` and a slide's text is `draw:frame > text:p`. Body text comes from `text:p`/`span`/`h`/`a` in `content.xml` and `styles.xml` (the latter carries running headers and footers); metadata comes from the `meta.xml` chardata elements, taken from the extractor's own `odfMeta` struct rather than from the spec, so the redactor covers exactly what the SCANNER reports. **The container rule was the hard part.** ODF 1.2 §3.3 requires `mimetype` first and STORED, and Go's zip writer additionally STREAMS: both `Create` and `CreateHeader` set general-purpose bit 3 and defer the CRC and sizes to a trailing data descriptor, leaving zeros in the local header. Measured on the first local header — `CreateHeader` gives `flag=0x0008 crc=00000000 csize=0 usize=0` and **LibreOffice refuses the file** (`source file could not be loaded`); `CreateRaw` gives `flag=0x0000 crc=0c32c65e csize=39 usize=39` and it opens. Nothing cheaper caught this: with the descriptor form `file(1)` still said `OpenDocument Text`, zip integrity passed, and both XML parts parsed. Isolated by rebuilding the same parts with python — a package with mimetype-stored-plus-deflated-rest opened, and so did one carrying BOTH redacted parts, which ruled out the compression mix and the rewritten XML and left the container. Verified end to end with the real reader: `soffice --headless --convert-to` opens all six forms and reads back the MASKED values (`***-**-9384`, `a**********@corp.example.com`), and `.ots` loads as a Calc document. `meta:template` is deliberately not covered — its value is an `xlink:href` **attribute** and this walker rewrites character data only, so a reported template path fails the residue check and the write is refused with the value named, which is the disclosed outcome rather than the silent one. Closes [#514](https://github.com/awslabs/ferret-scan/issues/514).
- **ipaddress:** stop reporting a four-part software version as an `IP_ADDRESS` at HIGH, and stop a document-level score from overriding a per-value cap. Two independent causes, and the more interesting one is the second. (1) The validator already caps a context-free dotted quad at 75 because a software version is structurally identical to a routable address — but it capped its LOCAL variable, and the dual-path bridge then adds a document-context adjustment to every match a validator returned, so the cap did not survive. Measured on ten real `.odt` documents carrying a **byte-identical** `LibreOffice/NN.N.N.N$MacOSX_AARCHNN` generator string: eight reported HIGH 95 and two MEDIUM 75, the whole difference being body text the match has nothing to do with. The cap is now published as a `confidence_ceiling`, the mechanism the bridge already had for exactly this and whose doc comment already described this defect ("no amount of surrounding context should promote it"); `docs/proposals/CONFIDENCE_CONTRACT.md` had also flagged the 75 cap as a cliff a +15 boost would cross. (2) The cap-escape is a keyword search over the match's own LINE, so one `http` anywhere on it lifted a version to HIGH — a User-Agent logged beside a URL scored HIGH 92. A **product-token shape** now outranks that: per RFC 9110 §10.1.5 `product = token ["/" product-version]`, a quad preceded by `/` whose preceding character is a LETTER is a version. The letter test is what separates `LibreOffice/24.8.4.2` from `http://52.94.236.248`, where the quad is also preceded by `/`; a rule keyed on the slash alone would have demoted all 10 URL-authority addresses in the corpus. A port or CIDR suffix is welded to the value and still wins, so `Gateway/52.94.236.248:8443` stays HIGH. Making the cap stick would on its own have demoted **4,549 genuine public addresses** in one real CloudTrail CSV export, because the escape searches the match's line while a CSV keeps its label in the header ROW — so the fix also resolves each match to its column header via `internal/tabular`, the package built for that same newline-bounded gap. Header keywords only ever ADD corroboration; there is deliberately no "header contradicts" arm, since suppressing an address on the strength of a column name would be suppression chosen by whoever wrote the file. Precision-only, measured across 2,198 real files: **0 findings lost, 0 gained**, 12 demoted out of HIGH (all 12 verified versions — 8 LibreOffice generators, 4 Chrome User-Agents) and 4,674 genuine addresses raised from HIGH 95 to HIGH 100 by the header arm. Closes [#513](https://github.com/awslabs/ferret-scan/issues/513).
- **ssn:** a CSV column of business identifiers is no longer reported as SSN at HIGH. The tabular header was already read, but only as a NEGATIVE signal drawn from a fixed ~45-word list — so `tracking_number` and `permit_number` were correctly capped at 55 while a header naming a DIFFERENT identifier that nobody had added to that list got no demotion at all. Measured on 500-row CSVs of SSN-shaped values, one column each: `parcel_id` **500 at 100 HIGH**, `meter_number` 498 at 100, `record_id` 495 at 100 (the pattern includes `\b\d{9}\b`, so undashed business IDs are swept in too). A second arm now tests the header's SHAPE rather than its vocabulary: a `<qualifier>_id` / `_number` / `_no` / `_code` header caps at 55 unless the qualifier names an identity document or a person. **The distinction is person-qualified versus thing-qualified** — a parcel, a meter and a shipment are not people, a member and an employee are, and US benefits and payroll exports really do key on the SSN itself. Two earlier versions of the rule were wrong in opposite directions and both were caught by tests already in the tree rather than by review: ignoring the qualifier demoted `employee_number` while `employee_id` stayed at 100 — the same concept split by its suffix, which is the very inconsistency this fixes — and excluding `member`/`participant` contradicted the scorecorpus, which labels `c19_honest_member_id` and `c20_honest_participant_id` **BandHigh** with the rationale "Real-world layout that must not hide an SSN from the redactor". A qualifier made only of identifier words (`id_number`) names nothing in particular and is not capped, matching `c17_honest_id_number`. **This CAPS, it never drops:** 55 keeps the value REPORTED and therefore still reaching the redactor — verified, redacting the capped `parcel_id` column still rewrites all 40 values with 0 cleartext survivors. Scored on the labelled corpus: **FP(H+M) 12 → 9 with the recall floor untouched** (`tp_high_medium` 154, `fn_missed` 0, `fn_band` 0), the three moving to `fp_low`; `internal/scorecorpus/testdata/baseline.json` is updated to lock that in. End to end the reported harm is gone — under a HIGH-gated pre-commit hook a `parcel_id` column went **rc=1 → rc=0** while an `ssn` column still blocks at rc=1. The cap remains tabular-only, so prose is untouched. Closes [#389](https://github.com/awslabs/ferret-scan/issues/389).
- **office:** extract ODF metadata, so a creator name or an email in `meta.xml` is no longer invisible at exit 0. `.odt`/`.ods`/`.odp` were already in `officeExtensions`, so `IsOfficeFile` was true and the office metadata preprocessor CLAIMED them — and then `ExtractMetadata`'s format switch fell through to `unsupported file format: .odt`, the preprocessor returned that error, the router quietly moved on to the text extractor, and `meta.xml` was never read on any ODF document. Three layers each behaved reasonably and the value vanished between them; nothing said the metadata had been skipped. That fatal fired on ONE wall-clock pair, before the median was ever computed, in a file whose own comment says a single pair is not a statistic — so the control was strictly weaker than the guard it validates. The median assertion that remains is stronger and is what the guard actually judges. Verified in both directions: hoisting the rescan out of the loop (making the fixture linear) still fails the control at a **4.18x median**, and under deliberate CPU contention at load 4.78 the medians read 15.5x-16.0x — tighter than before the warm-up, which is the noise the warm-up removes. Pre-existing on main; it surfaced on [#565](https://github.com/awslabs/ferret-scan/pull/565) and [#567](https://github.com/awslabs/ferret-scan/pull/567), neither of which touches this file.
- **redaction audit:** `redacted_file_hash` in the audit log is now populated, so the log attests to the artifact that was actually written. `SetRedactedFileHash` existed and had **no callers**, so the field was empty in every audit log ever produced, for every redactor and every file type — the log recorded the input's digest and a list of replacements, but nothing tied it to the bytes a downstream consumer receives, which is the only reason a compliance reader opens it. Set in `CreateAuditLog` via the existing streaming `HashFile`, which is reached from `AddRedactionResult` only after the redactor has returned successfully, so the output is already on disk (verified by recomputing the digest with an independent sha256 over the written file, not by comparing `HashFile` to itself). Both hash fields are now `omitempty`: a redactor may legitimately decline to write an output — the Office redactor refuses a partial redaction rather than emitting a leaky file — and a declared-but-empty field cannot be told apart from a computed-empty one, whereas a sha256 is never legitimately empty, so absence now means exactly "no artifact to attest to". A refused redaction never reaches the audit log at all (`total_documents: 0`), so no misleading entry is written either. Closes [#401](https://github.com/awslabs/ferret-scan/issues/401).
- **office:** inflate each embedded part once per scan instead of twice, bound the embedded part COUNT at 4,096 per container, and correct `embedded.BudgetBytes`' comment, which claimed to be a whole-traversal budget while the code grants a fresh per-container allowance. Every part used to be written to a temp file twice — once to decide metadata membership, once for scanning — so a 2-part `.docx` produced 4 temp files; the parts are still inflated for the admission verdict (it decides `EmbeddedMediaCount` and the `EmbeddedMedia_N_*` indices, which validators scan) but no longer written to disk. Measured: 40 parts x 5 MB 390ms -> 290ms, 2,000 tiny parts 2110ms -> 1390ms, output byte-identical on 381 real Office documents carrying 2,675 embedded parts. Separately, neither existing cap bounded the part COUNT — an empty part charges nothing against the 50 MB per-part cap or the 200 MB byte budget — so a 25 MB `.docx` declaring 200,000 empty parts cost 184s and 1.18 GB RSS; with the cap, 4.1s and 156 MB. 4,096 is ~11x the largest part count in 420 real Office documents (361), and report output is byte-identical across all 420. Parts past the cap are DISCLOSED on their own line with their own cause, naming the container's true total, never dropped silently. Closes [#379](https://github.com/awslabs/ferret-scan/issues/379).

### 🔨 Internal

- **detector:** new `Match.SourceKind` field (zero-value `SourceKindFile`) classifies match origin. `SARIF` and `gitlab-sast` formatters skip path-normalization (`%SRCROOT%`, basename rewriting) for matches with `SourceKindVirtual`. JSON serialization is omit-when-empty so existing consumers see no change.

Both fixes were mutation-verified against the restored regression. Closes [#504](https://github.com/awslabs/ferret-scan/issues/504).
- **position correlation:** delete a correlation method that could never be returned. `CorrelationContextual` and its scorer were dead in two independent ways, and both were re-proved before deleting anything. **The arithmetic:** `calculateContextualMatchConfidence` has an analytic maximum of exactly **0.75** — measured as the max over 20,001 inputs including the best case of identical contexts — against a gate of **0.8**, and the gate is immovable because `SetConfidenceThreshold` has **zero call sites** (the same-named methods on the plaintext, office and image redactors set their own fields, not the correlator's). **The reachability:** proved by execution rather than grep. A temporary counter and panic probe in `CorrelatePosition`, with a positive control at function entry, recorded **6,655 correlations across the full test suite and a 17-file-type corpus x 3 redaction strategies, with 0 branch entries** — and the positive control fired on all 6,655, so the zero is a measurement rather than an unwired probe. Forcing entry confirms why: with fuzzy disabled the scorer returns 0.6825 against the 0.8 gate, and the only state the default configuration can enter the branch in is "target absent from the document", where `findBestContextualMatch` returns nil because it requires at least one verbatim occurrence. **Deleted rather than re-gated**, because lowering a gate changes behaviour while removing unreachable code does not. 148 lines go: the enum value, its `String()` case, the branch, `tryContextualMatch`, `calculateContextualMatchConfidence`, the `ContextMatch` type, `findBestContextualMatch`, `findAllOccurrences`, `extractExtractedContext` and a now-unused import. The fuzzy branch is deliberately untouched and is now pinned by test — deleting it is the mutation that matters most, and it fails four assertions. **Zero behaviour change, proven rather than asserted:** across 17 file types, findings JSON is byte-identical on all 51 comparisons once the nondeterministic `duration_seconds` is normalised (the normaliser sanity-checked against a same-binary self-diff), redacted bytes are identical 17/17 for both `simple` and `format_preserving`, and for `synthetic` — where two runs of the SAME binary differ on 16 of 17 files, and 3 differ in length, so neither bytes nor length is a valid oracle — the redaction audit log was compared instead: **474 redaction decisions, 0 mismatches**, including the per-site `confidence` field the deleted branch would have influenced. A leak audit recursing into zip members found identical sets of surviving values before and after, with a per-file positive control asserted present so an all-clean report could not come from an empty file. Golden and the scorecorpus baseline are both untouched, which is the check that would have caught a behaviour change. Also corrected: the `PositionCorrelation.Method` doc comment listed `contextual` as a value it can hold and omitted `heuristic`, the value it actually falls back to.
