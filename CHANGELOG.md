## [Unreleased]

### 📚 Documentation

- **quotas:** correct the performance and error tables in `docs/reference/quotas-and-limits.md`, where **every row of the "Processing and Performance Limits" table was false** and had been since the project's first commit. It advertised Maximum Workers 32 ("regardless of CPU count"), a 2-worker floor "always maintained", a 1GB memory-pressure threshold, 250MB/10MB file-size worker scaling, and a 10MB chunk size with 1KB overlap — all marked **Configurable: Yes**. The real pool is `min(NumCPU, 8)`, derived *from* the CPU count, with no flag, config key or environment variable input; there is no memory-pressure detection, no file-size worker scaling and no chunking. Rows 1-3 were verbatim copies of `DefaultResourceLimits()` in `internal/parallel/resource_monitor.go` and rows 6-7 of `ChunkSizeMB: 10` in `internal/preprocessors/streaming_processor.go`, both deleted as never-wired dead code (`8cf13a6`, `00547f7`); the 250MB row never matched even the dead code, whose thresholds were 100MB/10MB and adjusted *batch* size. Two documented errors the tool cannot emit are removed — `File too large: chunk offset exceeds int32 maximum` ("File exceeds ~214GB"), whose string has only ever existed in this document, and `System under memory pressure`, whose advice to "reduce worker count" is impossible — along with the `Theoretical Maximum ~214GB` row resting on the same non-existent bound. The refusal table now lists all four real messages with the component that emits each, having previously misattributed the plain-text preprocessor's to the web UI and omitted the web UI's own. `parallel.MaxFileWorkers` and `parallel.FileWorkers()` are named so the number has one source, and four tests read the document itself so it cannot drift again. Also: `docs/user-guides/README-Preprocess-Only.md` no longer shows a `max_file_size` key under `text_extraction` (verified to print `Warning: unknown config key "max_file_size" — ignored`), and `docs/development/content-routing-troubleshooting.md` gains a warning banner — 29 of the 31 config keys and all 17 flags it documents do not exist ([#503](https://github.com/awslabs/ferret-scan/issues/503)). Closes [#411](https://github.com/awslabs/ferret-scan/issues/411).

### 🔒 Security

- **web:** bind to loopback (`127.0.0.1`) by default. Closes [TM-01](THREAT_MODEL.md). Container runtimes (Docker/Podman) auto-detected via `/.dockerenv` or `FERRET_CONTAINER_MODE=true` env var keep binding to `0.0.0.0` so port-publishing semantics work; bare-metal users get loopback-only by default. New `--bind <addr>` flag for explicit override (with stderr warning when bound to a non-loopback interface).
- **web:** add Origin/Referer validation on POST/PUT/DELETE/PATCH for `/scan` and `/suppressions/*`. Closes [TM-02](THREAT_MODEL.md). Non-browser callers (curl, scripts) that send neither header are allowed — they aren't subject to CSRF.
- **web:** emit baseline security headers on every response — `Content-Security-Policy` (`default-src 'self'` with `'unsafe-inline'` for the existing template), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`. Closes [TM-03](THREAT_MODEL.md). Strict CSP (no `'unsafe-inline'`) deferred pending template refactor — tracked as TM-05.
- **web:** suppression endpoints now inherit the loopback trust boundary. Closes [TM-04](THREAT_MODEL.md).

### ✨ New Features

- **video:** scan and redact `.3gp`/`.3g2`, and read the Apple `keys`/`ilst` metadata that iPhone and macOS recordings actually use. Four separate gaps in the same container, each measured on a real file. **`.3gp`/`.3g2` were not scanned at all** — the same ISO base media container as `.mp4` with a 3GPP brand — and the failure was SILENT: a real ffmpeg-written `.3gp` carrying an SSN in its 3GPP `dscp` box reported `No matches found.` at exit 0, with `--fail-on-incomplete` also exiting 0 and disclosing nothing, so the value was neither reported nor redacted. Registering the extension proved necessary but not sufficient: the twelve **3GPP asset boxes** (`titl` `dscp` `cprt` `auth` `perf` `gnre` `albm` `yrrc` `kywd` `rtng` `clsf` `perm`, per 3GPP TS 26.244) use a `[version][flags][language][NUL-terminated UTF-8]` payload, not the QuickTime `[length][language][text]` form, so with the extension registered and the boxes unhandled the file reported `Status: Success  MimeType: video/3gpp` and still produced zero findings — a "supported" format extracting nothing, whose clean result then looks authoritative. **Apple's `keys`/`ilst` pair** was unreachable four times over: `parseMoovBoxWithContext` had no `meta` case so a `moov`-level `meta` was never visited; `parseMetaBoxWithContext` skipped four version/flags bytes unconditionally, which is right for an ISO FullBox but wrong for QuickTime's plain container, so it read the first child's type `hdlr` AS ITS SIZE (0x68646c72 = 1,751,411,826) and abandoned the box; `keys` was never decoded into the index→name map that an `ilst` item's numeric type refers to; and an index-typed item fell through to a `default` arm gated on a length-only `isFourCC`, landing under a key made of raw bytes. The reader did not merely lose those values — `searchAppleMetadataInData` scraped raw text for `com.apple.quicktime.<field>` and took the bytes that follow, which in a keys table is *the next key's name*, so on a real macOS recording `CameraMake` read `m.apple.quicktime.model`, `CameraModel` read `m.apple.quicktime.software` and `CreationDate_Apple` read the literal atom type `data`, against true values `Apple`, `Mac16,6` and `macOS 15.2 (24C101)`. The scrape now stands down for any key the table answered. Also: `trak > udta` and `trak > meta` are read (`udta` was movie-level only, so a per-track comment was invisible); the eleven inner box walkers now honour the two special ISO size words via a shared reader, where a size of `1` previously failed the `size < 8` check and **ended the walk**, taking every later sibling with it; a `data` box's well-known type indicator is honoured so a binary payload is no longer stringified into the scanned text, while a mislabelled UTF-8 payload is still read; `parseDate` accepts Apple's colon-less zone offset; and the video redactor claims `.3gp`/`.3g2`, without which a newly-found value was reported and then disclosed as `no redactor registered for file type: .3gp`. Verified end to end: redacting a real `.3gp` writes a same-size file that `ffprobe` still recognises with the cleartext gone. Closes [#431](https://github.com/awslabs/ferret-scan/issues/431) and [#400](https://github.com/awslabs/ferret-scan/issues/400).
- **cloud-resources:** new Cloud Resources Validator detects cloud provider resource identifiers across six major cloud platforms. Supported providers: AWS (ARNs with 12-digit account IDs), Azure (Resource IDs with subscription UUIDs), GCP (resource names with project IDs), OCI (OCIDs), IBM Cloud (CRNs), and Alibaba Cloud (ARNs). Key features: provider-specific metadata extraction (account ID, resource type, region), confidence scoring with contextual analysis, configurable per-provider enable/disable, and custom pattern support via configuration. New validator ID: `CLOUD_RESOURCES`.
- **stdin:** read content to scan from standard input via `--stdin` or the POSIX-style alias `--file -`. Content is treated as plain text and findings are labelled `<stdin>` (configurable via `--stdin-name`). Useful for `git diff | ferret-scan --stdin`, scanning command output, and lambda/IPC callers that already have content in memory. Mutually exclusive with `--file <path>`, positional file args, and `--web`. Max input size: 100 MB.
- **stdin redaction (streaming gateway):** combine `--stdin` with `--enable-redaction` to act as a streaming redactor — redacted content streams to stdout while findings go to stderr (or `--output <file>` if specified). All three plaintext strategies (`simple`, `format_preserving`, `synthetic`) are supported. Suppressed matches pass through unmodified. When findings stream to stderr alongside redacted content on stdout, human-readable progress lines are suppressed so the findings document remains parseable (canonical shape: `... --enable-redaction --format json 2> findings.json > clean.txt`). When stdout is a terminal (interactive use, no redirect), findings are replaced by a one-line hint pointing at the pipe shape — this matches the `git diff` / `jq` convention of adapting output to the consumer.
- **api:** new `core.ScanContent(content, ContentScanConfig)` entry point for in-process callers — scans an in-memory buffer using the same validator pipeline as `ScanFile` but bypasses the path-driven file router.
- **api:** new `plaintext.PlainTextRedactor.RedactString(content, matches, strategy)` exposes pure in-memory redaction without requiring an output manager — the same code path that drives streaming stdin redaction is now available to lambda / gateway callers.
- **api:** new `redact.ValidCheckNames()` returns the sorted validator IDs accepted in `EngineOptions.Checks`. `NewEngine` silently drops names it doesn't recognize and only errors when the resulting set is empty, so a typo in a mixed list (e.g. `{"CREDIT_CARD", "emial"}`) otherwise fails *open* — the misspelled validator is quietly disabled and that data type passes unredacted. Callers wanting fail-closed behaviour can validate their `Checks` against this list and reject unknown names before constructing the engine. The `lambda-redact` example now does exactly this at `init()`.
- **explain:** new `--explain` flag annotates each finding with a plain-language rationale, a verdict (`likely_real` / `likely_test` / `uncertain`), and a drafted suppression reason. Fully offline and deterministic — it only re-phrases signals the detection engine already computes (validation checks, vendor, context impact, file location); no network calls, no new dependencies, nothing leaves the host. Off by default. Renders in text (verbose + pre-commit), JSON/YAML (first-class `explanation` field), SARIF (result message + structured property), and gitlab-sast (description); with `--generate-suppressions`, generated rules carry the drafted per-finding reason. A HIGH-confidence finding is never glossed as `likely_test`, so the verdict can't talk a reviewer out of a real finding. New `internal/explain` package (`Explainer`, `SignalSynthesizer`).
- **api (pkg/scan):** `TextOptions`, `FileOptions` and `RedactFileOptions` gain `ConfigPath string` and `DisableConfigDiscovery bool`, so an embedded consumer can pin the config or opt out of ambient discovery entirely. Previously all three called `config.LoadConfigOrDefault("")` unconditionally with no config field on the options structs, so detection depended on the calling process's **working directory** with no way to pin it, no way to request built-in defaults, and no way to write a hermetic test. Verified with an identical `ScanText` call differing only in CWD: `findings=1` from one directory, `findings=0` from another holding a `.ferret-scan.yaml` with `disabled_types`. Same shape as the `redact.ValidCheckNames()`/`SOCIAL_MEDIA` case — a successful call, an empty finding list, input treated as clean — except the cause was ambient rather than in the caller's arguments, so the caller could neither detect nor prevent it. Both fields default to zero, so **existing callers are unaffected**: an empty `ConfigPath` keeps the historical discovery behaviour. `DisableConfigDiscovery` takes precedence when both are set, being the stricter request.

### 🐛 Bug Fixes

- **images:** the JFIF comment scan now WALKS the JPEG segment chain instead of byte-scanning for the pair `0xFF 0xFE`. A given byte pair turns up about once every 64KB of compressed data, so on a real JPEG the scan found noise and handed it to the validators as document text. Measured on an Apple-shipped asset (`/Applications/Numbers.app/.../9f5178abe0a74d6f0a905b2974c7c7a203b965.jpeg`, 139,103 bytes) which has **no COM segment and no Exif APP1** and exactly **one** `0xFFFE` in the whole file — at offset 557, **inside** the Display P3 ICC profile carried in APP2, which spans bytes 2–566 — declaring 59,392 bytes: extracted text went **210 → 59,599 characters** and the validators reported **five `SOCIAL_MEDIA` `TWITTER` findings at HIGH 100/91** (`@hf`, `@K_pIa`, `@am`, `@E4`, `@L_`) for handles present nowhere in the file. Those phantom findings then drove the image redactor, which decodes and re-encodes: a "redacted" copy **was written for a file holding nothing**, 139,103 → 95,213 bytes, with **418,816 of 487,080 decoded pixel bytes different (85.99%**, max channel delta 60) and the **ICC profile gone**. A lossy redactor must act on "this part holds a reported value", and here the value was an artefact of the reader. This was reachable only after [#480](https://github.com/awslabs/ferret-scan/issues/480) stopped `ExtractExif` returning early on a failed EXIF decode — correct in itself; the `isJPEG` gate added there excludes PNGs, but a JPEG's own compressed bytes are exactly where this collision lives. Walking is the fix rather than a tighter length check, because no check on the length can tell a marker from two bytes that merely look like one: a COM segment is one only if the chain leads to it, and the walk stops at SOS where markers stop being addressable. A genuine COM segment is still recovered, including after APP0/APP2/DQT segments, behind fill bytes, and after payloadless restart markers. Closes [#490](https://github.com/awslabs/ferret-scan/issues/490).
- **images:** the 4MB PNG text budget is now consulted BEFORE a chunk is read or inflated. It was checked after `parsePNGText`, which is where the zlib inflation happens, so the WORK was bounded by `maxPNGChunks × maxPNGTextChunkBytes` — 65,536 × 1MB, i.e. **64GB of decompression** — rather than by the 4MB of text actually kept. Both caps existed and were individually correct; they simply did not compose in that order. Measured on valid PNGs whose only additions are N `zTXt` chunks, each ~1KB compressed and inflating to exactly the 1MB per-chunk cap: a **69.4MB / 65,535-chunk** file cost **81.27s and 135MB RSS** against 0.09s and 30MB before this reader existed, and was reported at **rc 0 as a fully scanned clean file**; 2,000 chunks already cost 7.95s. After the fix the cost is **flat across a 14,000× range in chunk count** (5.0–6.1s from 5 to 65,535 chunks) because it is bounded by the cap rather than the file — recovered text is exactly 4.00MB in every case. The residual is the validators reading that bounded 4MB, which is what any PNG legitimately carrying 4MB of text costs. `eXIf` is exempt from the budget: it is not text, does not draw on it, and is the one chunk whose loss would be a coverage regression rather than a saving, so the skip continues the walk header-only instead of stopping it. Ordering note: `decodePercentEncoded` still runs before the cap, deliberately, so the budget counts scanned text rather than its encoded form — what moved is the inflation. Closes [#491](https://github.com/awslabs/ferret-scan/issues/491).
- **images:** decode a percent-encoded PNG text chunk before scanning it. A tool that stores a document inside a text chunk commonly percent-encodes it — draw.io writes the diagram source into a `tEXt` chunk keyed `mxfile`, run through `encodeURIComponent` — and scanning that as-is costs recall AND precision at the same time, which is why decoding is a fix rather than a trade. `Employee%20SSN%20449-87-4100` reported **0 findings** while the same text unencoded reports SSN: `%20` glues characters to the value so no pattern matches, and only reported findings reach the redactor, so it was a silent miss. Measured end to end on **2,500 real PNGs** from this host: **526 findings → 130**. Of the 425 lost, **every one is `RECOVERY_CODES` at MEDIUM** — percent-encoded XML fragments (`%3C`, `%22`, hex-ish runs) read as codes — and **zero were in the HIGH band**, so no real value was lost. 29 are gained, and they are reported honestly rather than counted as all wins: 6 `IP_ADDRESS` at **HIGH** (dotted quads out of decoded network diagrams, genuine and previously unreachable), 1 `INTELLECTUAL_PROPERTY`, and **22 `PHONE` at LOW/MEDIUM on a bare six-digit run, which are new false positives**. The gate is "does the text hold at least one VALID `%XX` escape", chosen over two narrower alternatives after measuring all three across **5,989 real PNGs** (1,645 carrying a text chunk, only **18** containing a `%` at all): keying on the `mxfile` keyword would cover one vendor and not the next tool, and keying on `%3C`/`%3E` — an encoded `<` — was the first version and is derived from the XML population, so it misses a payload encoded WITHOUT markup, which is exactly the reported recall case. The wide gate is measurably free: the only real chunks it newly considers are two Adobe XMP packets, and a decode leaves them **byte-identical**, because their `%` is not followed by two hex digits. Residual risk stated rather than hidden: prose containing a percent followed by two hex-ish characters (`50%2B off` → `50+ off`) would be altered; nothing like it appears in 5,989 real files, and a mangled metadata string costs at most one chunk whereas not decoding costs a silent miss. The decoder is **lenient** rather than `url.PathUnescape`, which fails the whole string on one malformed escape — a payload that is only partly encoded would then stay entirely encoded, turning a precision fix into a recall miss. `+` is deliberately not treated as a space: that is form encoding. Decoding runs after inflation, so it reaches a **deflated** `zTXt` payload that no byte scan could, and BEFORE the size caps, so the budget counts what is actually scanned — an encoded payload is up to three times its decoded size, so counting the encoded length would exhaust the 4MB total on a third of the real content and silently drop later chunks. Decoding strictly shrinks the payload, so it adds no expansion bound. Closes [#481](https://github.com/awslabs/ferret-scan/issues/481).
- **office:** macro-enabled OOXML (`.docm`, `.xlsm`, `.pptm`) is now scanned. It was not scanned **at all** — a `.docm` whose `word/document.xml` and `docProps/core.xml` are byte-identical to a `.docx` reported **0 findings at exit 0 with no disclosure**, where the `.docx` reported 2; a properly-built `.xlsm` and `.pptm` reported 0 where their `x` counterparts reported 4. The root cause was **seven disagreeing extension lists**: the macro forms were registered in `plaintext_preprocessor.go` and `redactors/manager.go` and absent from every site that does the work — including a direct contradiction where `manager.go` routed `.docm` to the office redactor whose own `GetSupportedTypes()` said it did not support it. The decisive one was `officeExtensions` in `shared_utilities.go`, because the router's `isBinaryDocument` derives from it through `IsOfficeFile`: while the macro forms were missing there, the file was rejected before any preprocessor was consulted, so nothing further down the pipeline could have helped. These are the same ZIP container as their plain counterparts — a different content type plus a `vbaProject.bin` — so each one dispatches to the existing reader rather than to a copy of it, and body text, `docProps` metadata and redaction all work unchanged. Verified as a **control pair** in every case: byte-identical parts under both extensions, with the plain form scanned in the same test, because asserting only that the `.docm` reports would also pass on a reader that ignored the extension and sniffed the ZIP — a different fix with different consequences for the redactor. The documentation asserted coverage the whole time: `docs/reference/quotas-and-limits.md` says "An OOXML container (`.docx`, `.xlsx`, `.pptx` **and their macro-enabled forms**) can hold arbitrarily …", which requires them to be processed before any budget could apply. Seven other doc files that listed the `x` forms only are corrected. Closes [#497](https://github.com/awslabs/ferret-scan/issues/497).
- **office:** an embedded part whose reported value is spelled with an XML character reference is no longer judged clean and skipped. The admission gate asks "does this part hold a reported value" with a raw byte search, so a part spelling the value differently from the way it was reported looked empty — and because the gate treats "nothing found" as permission to SKIP the part, that blindness was a leak rather than a missed optimisation. Measured on a `.docx` carrying `word/embeddings/inner.docx` whose `document.xml` held `Patient SSN 449-87-410&#48;` (the final `0` as a decimal reference): reported as one SSN finding, then skipped, and Python `ElementTree` read `449-87-4100` straight out of the "redacted" file at **exit 0 with no warning**. Both controls redacted correctly — the same value spelled plainly in the same embedded part, and the same escaped value at TOP level — which is what localises the defect to the gate: `rewritePartText` already matches character data on its DECODED form and re-emits it escaped, so the redactor was always capable. The fix therefore yields **full redaction, not a refusal**: the inner text node becomes `Patient SSN ***-**-4100`, the character reference is gone, and both zips and every XML part still parse. The gate now searches the part's bytes AND the same bytes with references resolved, because enumerating spellings cannot work — `&` introduces character references, so any character at any offset can be respelled in decimal or hex with arbitrary leading zeros, and `449-87-410&#48;`, `&#52;49-87-4100` and `449&#45;87&#45;4100` are all the same SSN. `embedded.XMLEscapeVariants` still contributes the five predefined entities, covering the opposite direction where a value is REPORTED in escaped form. The decoder moved to a new stdlib-only leaf, `internal/xmlref`, because a second caller now needs the identical answer and two copies of a codec that decides whether a value is PRESENT is how the two halves drift apart — `internal/redactors/tagmeta` switched to it, so there is one implementation. Cost: one decode per part rather than per value, so the work stays linear in part size, and `xmlref.Decode` returns its input unchanged **without copying** when there is no `&` at all — the overwhelming majority of embedded parts, since most are binary. Dispatch is lossy (the image redactor re-encodes and strips metadata), so the widened gate is tested in both directions: a part full of legal references but holding no spelling of the value is still skipped. Closes [#475](https://github.com/awslabs/ferret-scan/issues/475).
- **redaction:** a reported value is no longer redacted at the WRONG occurrence and left in cleartext. `tryExactMatch` and `tryFuzzyMatch` in `internal/redactors/position/correlator.go` resolved a match with a **document-wide** `strings.Index`, ignoring the `Line` they were handed, so they always returned the FIRST occurrence of the value whatever line it was reported on. Where a value occurs more than once that answer is wrong, and the wrong offset reached the redactor. Measured on a two-line file — `creditcard VISA 4532 0151 1283 0366` then `Call 0151 1283 0366 for support.` — the PHONE reported at **HIGH 100** on line 2 was resolved to offsets 21-35, which lie inside line 1, so **line 2 came back byte-identical to the input** with `Success: true` at rc 0 and no disclosure, on **all three strategies**. Only reported findings reach the redactor, so a value it skips is left in cleartext with nothing saying so.
  **The uniqueness penalty that exists to catch this was bypassed by exactly 0.0.** For a value occurring twice, `exactMatchConfidence(2)` = `0.95*(0.5+0.5/2)` = **0.7125**, below the 0.8 gate at `plaintext/redactor.go:229`, so the exact path was correctly REJECTED — but `calculateFuzzyMatchConfidence` returns `0.8*1.0` = **0.8** for an edit distance of 0 and the gate is `>=`, so the fuzzy path admitted the same offset the exact path had just refused. Both paths are now scoped to the reported line, rather than relying on a confidence gate to reject a wrong answer.
  **A second harm, same cause:** resolving the line-2 report onto line 1 rewrote the bytes the VISA replacement was about to rewrite, so the VISA then found text that no longer matched and its replacement was **silently skipped** — the log recorded `text_mismatch_warning` instead of `redaction_applied`, and line 1 read `4532 **** **** 0366`, which is the PHONE's mask landing in the wrong place rather than the card being redacted. Across 734 real redacted files the count of skipped replacements fell **36,234 -> 2,381**; note that not every mismatch is a defect, since a contained match legitimately mismatches once its enclosing match has masked those bytes.
  Measured across **1,009 real text files** producing 734 redacted outputs and 28,456 reported lines: lines left **completely untouched where a finding was reported** fell from **368 across 116 files** to **2 across 2 files**, and the 2 that remain are a separate defect ([#522](https://github.com/awslabs/ferret-scan/issues/522) — already-masked text re-detected as a secret and "redacted" asterisks-for-asterisks, where no value is at risk). Detection is **bit-identical**: 57,786 findings on both binaries, 0 lost, 0 gained. The scoped form is also consistently **faster** — 1.08x to 1.48x across 1,000-8,000 matches, never slower, because resolving document-wide took two whole passes per match and scoping takes one plus per-line work; the residual superlinear growth is pre-existing and not addressed here. A document-wide fallback is kept for a match whose recorded line does not contain its text (a bounded or consolidated match, or extractor line drift), so such a match is still located and still redacted exactly as before. Closes [#519](https://github.com/awslabs/ferret-scan/issues/519).
- **audio:** a FLAC block or field that declares more than it holds is now read to what exists and DISCLOSED, instead of being discarded in silence. [#476](https://github.com/awslabs/ferret-scan/issues/476) correctly removed an allocation bomb by clamping the block read to the bytes the file holds, and that clamp stays — but it exposed two behaviours behind it. **(1) A cleartext leak.** `parseVorbisComments` discarded any field whose declared length ran past the buffer, and every LATER field with it, because the bound was a `break`. Before the clamp the buffer was sized to the *declared* length with a zeroed tail, so the bound passed — for the wrong reason, by comparing against invented zeroes — and the partial field reached the validators. Measured on a real libFLAC encode (ffmpeg, from `/System/Library/Sounds/Submarine.aiff`) with `PADDING` dropped so `VORBIS_COMMENT` is genuinely last, then truncated five bytes past an SSN: **before #476 `PERSON_NAME` + `SSN` with 0 cleartext SSN in the redacted copy; after #476 `PERSON_NAME` only with 1 cleartext SSN**. The untruncated file reports 2 findings on both, and exiftool, ffprobe and ffmpeg all read it cleanly, so the difference is specifically the truncation. The value is complete in the bytes that ARE present — only the padding after it is missing — so the fix is the same principle #476 applied one layer up: clamp to what exists, and use it. **(2) A lost disclosure.** The old read returned `io.EOF` when *zero* bytes were available, which propagated out as a parse failure and produced `cannot parse` at rc 3; clamping returns a short buffer and no error, so a 46-byte file whose `VORBIS_COMMENT` payload is entirely absent, and the 8-byte #457 bomb itself, both went from **rc 3 to a silent rc 0**. Declared-vs-present is now checked at the BLOCK level too, because the field-level check structurally cannot see a payload that is entirely absent (the parser returns on its short-buffer guard first) and because the block check also covers `STREAMINFO`. The vendor string is a third over-declaring site and is disclosed as well. Two distinct warnings, because the remedies differ: a short *block* means the file is truncated or corrupt, a short *field* means one tag is unreliable. Both go through `ExtractionWarning`, the channel the WAV path already uses for its exact sibling ([#423](https://github.com/awslabs/ferret-scan/issues/423)), and both are payload-free (BSC4) — they name the spec's block type, never the document's field keyword or value. Net result is better than either binary: on the truncated-field fixture even pre-#476 reported at rc 0 with no disclosure, and this now gives rc 3 with the value recovered. A compliant FLAC still carries no warning. Closes [#493](https://github.com/awslabs/ferret-scan/issues/493).
- **audio:** clamp a declared box/block length to the bytes the file actually holds before allocating. Every length in these containers is read out of the file, so it is producer-chosen, and the only previous guard on the `.m4a` `mvhd` size was a floor (`size < 24`) — a **52-byte** `.m4a` declaring `0xFFFFFFFF` allocated 4096MB, and an **8-byte** `.flac` whose first metadata block declared `0xFFFFFF` allocated 16MB. End to end, a directory of six such `.m4a` files plus one real recording (220KB of input) reached 4.03GB of peak RSS in 2.57s; now 0.03GB in 0.74s. Note for anyone reproducing this class: a SINGLE bomb shows almost nothing, because Go does not zero a span taken fresh from the OS, so 4GB is reserved and never written — the pages only become resident once the runtime reuses a dirty span and must zero it. Also fixes a correctness defect in the same code: the buffer was sized to the declaration and a short read tolerated, so an `mvhd` claiming more than the file holds parsed its zeroed tail as a real creation date and duration. Field access is now bounded by the bytes actually read. Verified on 600 real audio files (548 `.m4a`, 50 `.wav`, 2 `.mp3`): report output byte-identical, 17 findings, 0 empty outputs. Closes [#457](https://github.com/awslabs/ferret-scan/issues/457).

- **memory:** findings no longer pin the whole extracted buffer of the file they came from. Every string on a finding (`Text`, and the `FullLine`/`BeforeText`/`AfterText` context windows, plus content-derived metadata) was a Go substring of the file's entire extracted content, and a substring retains its parent's whole backing array — so one 16-byte finding kept that file's buffer alive until the process exited. `detector.DetachMatches`, called once at the scan convergence in `parallel.RunValidators`, replaces those strings with copies that share one allocation per line. Measured on 64 files of 2 MB with one EMAIL each (128 MB of input, 64 findings): peak RSS **248 MB → 109-146 MB**, which is the same band as scanning the identical bytes with **zero** findings (115-142 MB) — i.e. a scan that finds things now costs what a scan that finds nothing costs. Reported values are unchanged (byte-identical golden corpus, and suppression hashes are computed over values, so saved user rules keep matching). Two things this deliberately does not do: a document that is a single long line is left aliased, because there the copy would be as large as the buffer it frees; and it does not bound memory by finding COUNT, which is a separate retention term ([#337](https://github.com/awslabs/ferret-scan/issues/337) mechanism 2) in different files.

Measured: the same binary, flags and input went from 1 finding to 0 because of a file dropped next to the content, with **nothing in the output naming it**. One stderr note (`Note: using project config .ferret-scan.yaml found in the working directory; it can disable detection types.`) now makes the substitution visible. Deliberately quiet for an explicit `--config <path>` (the user chose it) and for a config in the user config dir (a standing preference), because a line on every run trains people to ignore it. Not gated on `--quiet`: that suppresses progress output, whereas which config governed the run is a disclosure, and in CI it matters more. New `config.Config.SourcePath` records the provenance and carries `yaml:"-"` so a config file cannot claim an origin it does not have. This does **not** close the underlying trust-boundary question — whether a config discovered inside the scan target should require opt-in — which is a threat-model decision tracked in #293.
- **audio/video:** map the XMP packet at `moov/udta/XMP_`, which is the MAJORITY QuickTime layout and was left opaque. [#477](https://github.com/awslabs/ferret-scan/issues/477) mapped the packet carried in a top-level `uuid` box; this is the other home, the one Adobe's XMP Specification Part 3 prescribes for QuickTime and the one `exiftool` writes for a `.mov`. A census over **1,178 real ISO-BMFF files** on this host found **90 carrying `moov/udta/XMP_` against 24 carrying the `uuid` form**, and none carrying both — so the unmapped layout was **3.75× more common**. The packet sat inside a span labelled `MP4 udta`, and every consumer reads a span's label as the answer to "is this XML character data" (`video.blockRegion` sets `XMLText: span.Label == LabelXMP`), so `tagmeta.ResidualEncoded` was **structurally blind** to it — and that check exists precisely because XML permits `&apos;`, `&#39;`, `&#x27;` and so on without limit, which no raw byte search can see. Measured on a real Apple-shipped `.mov` (4.9MB, a 17,450-byte `XMP_` packet) tagged with `exiftool -Title="Patrick O'Connor"`: `exiftool` writes the value to BOTH homes, raw in `ilst` and entity-encoded in the packet, the scanner detects it from the `ilst` copy, and the redacted file came out with the raw copy masked, **the encoded copy intact, and `exiftool` reading `Title : Patrick O'Connor` straight out of it at exit 0 with no warning**. Now that file is REFUSED with the cause named (`… remain … as XML-encoded text after redaction (e.g. an apostrophe written as &#39;) …`), rc 0 by default and **rc 3** with `--fail-on-incomplete` — the same choice #477 made for the `uuid` layout, since masking an encoded occurrence needs a decoder carrying an index map. The udta payload is **split** around the XMP child rather than double-recorded, because each span becomes an independent block the caller reads, modifies and writes back, so two spans over the same bytes would clobber each other; the siblings keep their raw-byte `MP4 udta` treatment, since running an entity decoder over binary tag boxes could resolve bytes that merely look like `&#NN;` into a value the file never held. The `XMP_` atom's own 8-byte header is in no span, so a same-length overwrite cannot damage its size or type. A child whose declared size overruns the payload falls back to one opaque span rather than guessing a stride — without that clamp the span measured `[24, 4294901776)`, a 4GB region from a 292-byte payload. A value with no encodable character still redacts normally, and files with no `XMP_` child are untouched. Closes [#499](https://github.com/awslabs/ferret-scan/issues/499).

Disclosures are untouched — a value naming a project, a person, an address or an account number still scores 100. A marking is demoted, never vetoed, and redaction is confidence-blind, so a demoted value is still masked in the redacted copy. Known limitation: a one-word remainder cannot be told from a status word, so `Confidential - Nightjar` is graded as decoration (zero occurrences in the 714 documents; still reported at MEDIUM, still redacted). ([#320](https://github.com/awslabs/ferret-scan/issues/320))
- **redaction audit:** `redacted_file_hash` in the audit log is now populated, so the log attests to the artifact that was actually written. `SetRedactedFileHash` existed and had **no callers**, so the field was empty in every audit log ever produced, for every redactor and every file type — the log recorded the input's digest and a list of replacements, but nothing tied it to the bytes a downstream consumer receives, which is the only reason a compliance reader opens it. Set in `CreateAuditLog` via the existing streaming `HashFile`, which is reached from `AddRedactionResult` only after the redactor has returned successfully, so the output is already on disk (verified by recomputing the digest with an independent sha256 over the written file, not by comparing `HashFile` to itself). Both hash fields are now `omitempty`: a redactor may legitimately decline to write an output — the Office redactor refuses a partial redaction rather than emitting a leaky file — and a declared-but-empty field cannot be told apart from a computed-empty one, whereas a sha256 is never legitimately empty, so absence now means exactly "no artifact to attest to". A refused redaction never reaches the audit log at all (`total_documents: 0`), so no misleading entry is written either. Closes [#401](https://github.com/awslabs/ferret-scan/issues/401).
- **office:** inflate each embedded part once per scan instead of twice, bound the embedded part COUNT at 4,096 per container, and correct `embedded.BudgetBytes`' comment, which claimed to be a whole-traversal budget while the code grants a fresh per-container allowance. Every part used to be written to a temp file twice — once to decide metadata membership, once for scanning — so a 2-part `.docx` produced 4 temp files; the parts are still inflated for the admission verdict (it decides `EmbeddedMediaCount` and the `EmbeddedMedia_N_*` indices, which validators scan) but no longer written to disk. Measured: 40 parts x 5 MB 390ms -> 290ms, 2,000 tiny parts 2110ms -> 1390ms, output byte-identical on 381 real Office documents carrying 2,675 embedded parts. Separately, neither existing cap bounded the part COUNT — an empty part charges nothing against the 50 MB per-part cap or the 200 MB byte budget — so a 25 MB `.docx` declaring 200,000 empty parts cost 184s and 1.18 GB RSS; with the cap, 4.1s and 156 MB. 4,096 is ~11x the largest part count in 420 real Office documents (361), and report output is byte-identical across all 420. Parts past the cap are DISCLOSED on their own line with their own cause, naming the container's true total, never dropped silently. Closes [#379](https://github.com/awslabs/ferret-scan/issues/379).

### 🔨 Internal

- **detector:** new `Match.SourceKind` field (zero-value `SourceKindFile`) classifies match origin. `SARIF` and `gitlab-sast` formatters skip path-normalization (`%SRCROOT%`, basename rewriting) for matches with `SourceKindVirtual`. JSON serialization is omit-when-empty so existing consumers see no change.
- **parallel:** extracted shared `parallel.RunValidators(ctx, validators, content, strategy)` helper from the worker pool. Worker pool now passes a retry-backed strategy; in-memory callers pass nil for direct invocation. Same dual-path / metadata-skip behaviour preserved.
- **tests:** two complexity guards no longer fail on a slow CI runner while the code is linear. `TestCreateBasicLineMappingsIsLinear` failed on macos-latest at a 12.3x wall-clock ratio against a 12.0x limit (base=7.44ms), while its own absolute ceiling passed with a 22x margin; the ratio is now measured in **allocated bytes**, which is the same defect without a clock — the regression re-splits the whole text per line, so it is O(n²) in bytes, measured 4.6x linear against 26.4x regressed, and byte-identical under `GOMAXPROCS=1`. `TestAssignLineColumnsComplexityDistinctAndRepeated` failed on windows-latest at 307ms against a 250ms ceiling — the only sub-second wall-clock ceiling in the repo, where every other complexity guard allows 2-20s — while its scale-free growth ratio correctly read 5.7x; the ratio is now the discriminator at 9x (evenly splitting a worst-observed 5.9x from a measured 13.6x) and the ceiling is the file's existing 4s catastrophe net. Both fixes were mutation-verified against the restored regression. Closes [#504](https://github.com/awslabs/ferret-scan/issues/504).
